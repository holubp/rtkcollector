# RtkCollector 1.0-RC9

Status: release preparation; not published or fully verified yet.

The alarms, Bluetooth extension and DND advisory are implemented. Eight findings
from the requested Astra audit have regression fixes and are undergoing
independent re-review and combined verification. Earlier checkpoint receipts
must not be treated as coverage of later fixes.

## Changes

- Recording alarms distinguish receiver connection/data loss, loss of usable
  positioning and recording/workflow interruption.
- Menu -> Alarms persists independent visual/acoustic choices and built-in or
  Android notification sounds for each category. Defaults are a low single
  repeating beep for position loss and a high triple repeating beep for receiver
  loss or recording interruption.
- Position alarms arm only after the first fresh valid fix, then use a configurable
  delay (initially five seconds). Initial acquisition and RTK quality downgrade
  alone do not alarm. Recovery automatically clears active disruptions.
- Deliberate Stop silences alarms before recording finalization. Terminal failure
  alerts may continue without retaining recording files/resources until Stop,
  acknowledgement or Android playback failure/timeout.
- Notifications are silent themselves; an isolated audio owner supplies sound.
  Watch and lock-screen delivery depends on Android and companion settings.
- USB recording uses the connected-device foreground type; acoustic alerts add
  media playback. The unnecessary data-sync type is removed.
- Optional Bluetooth alarm audio prefers a connected audio device and requests
  the phone speaker on disconnect or failed routing. Preferences default off,
  persist across restarts and also apply to preview. No global communication,
  speakerphone, volume or DND changes are made. Confirmed routing is shown in
  Alarms settings, separately from errors; physical audibility is not guaranteed.
- Home shows a nonmodal Do Not Disturb advisory while recording with acoustic
  alarms enabled. It never changes DND/volume or marks recording failed.
- USB recovery keeps retrying recoverable platform failures in the existing
  session, refreshes reattached device identity, and requires receiver bytes
  before declaring data recovery. Stop cancels queued TX before background
  finalisation; normal baud changes and probes exclude correction writes.
- Routine recording notifications run on a bounded independent delivery lane,
  so blocked Android notification calls cannot stall receiver capture.

## Verification And Limits

The clean Termux pre-push gate passed: 1,340 tests across 192 suites, with zero
failures/errors/skips, production/all JVM-test source compilation and IDE task
compatibility checks. Astra re-reviewed the full scope and all eight regression
fixes, with no remaining material source findings. Clean-host Robolectric/variant
tests and stable-signed APK publication are pending. No device/watch delivery, layout, screen-off, physical
Bluetooth or high-rate receiver smoke test is claimed. Local compilation is not
APK/AAB assembly or execution of host-only Android tests.

RC9 uses version code 10 and retains the existing stable signing identity.
Human:holubp explicitly approved the normal CHANGE_NETWORK_STATE permission and
RC9-specific use of checked-in gates, independent review and GitHub CI while the
strict-assurance integration is deferred ("all three approved"). This is not an
inherited RC8 exception or a strict-checker pass. Permission implementation and
the Bluetooth extension must be verified before publication.
